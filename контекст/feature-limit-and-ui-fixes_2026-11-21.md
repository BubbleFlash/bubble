## Лимиты запросов и управление политикой — #111

**Исторически подтверждено.** На сайте срабатывал `429` при поиске друзей. В API действовал общий лимит и отдельные лимитеры поиска, входа, восстановления сеанса, загрузок, жалоб, сообщений и других операций. Отключение только общего middleware оставило бы ограничения отдельных маршрутов. Конкретный источник ответа на пользовательском скриншоте не был доказан журналами production.

По указанию владельца HTTP-лимитеры приложения сделали выключенными по умолчанию. Добавили общий переключатель и отдельные правила с включением, числом запросов и окном в секундах. Начальные значения правил взяли из прежних порогов. Раздел доступен администратору.

Файлы — `packages/shared/src/rateLimits.ts`, `apps/api/src/models/RateLimitSettings.ts`, `apps/api/src/services/rateLimitSettings.ts`, `apps/api/src/middleware/rateLimit.ts`, `apps/api/src/controllers/rateLimitController.ts`, `apps/web/src/components/RateLimitSettings.tsx`.

Решения с долгосрочными последствиями:

- Политика хранится в MongoDB, а API кэширует её на пять секунд. Сохранение сбрасывает локальный кэш. Остальные экземпляры узнают об изменении при обновлении своего кэша.
- Для изменения длительности окна недостаточно изменить число разрешённых запросов. Для соответствующей версии правила создаётся новый middleware `express-rate-limit` с фиксированным окном. Прежний `MemoryStore` закрывается, чтобы убрать таймеры и старые счётчики.
- Ревизии позволяют начать новое окно после изменения правила и сохранить бюджет при повторной отправке тех же значений. Изменение одного правила не должно сбрасывать остальные бюджеты. Параллельные сохранения разных правил выполняются через атомарные обновления отдельных полей документа.
- Управление лимитами исключено из общего лимита IP. Иначе администратор с исчерпанным бюджетом мог бы потерять возможность выключить ограничения. Авторизация и проверка роли на этих маршрутах обязательны.
- Старый документ с одним общим переключателем должен читаться с исходными значениями отсутствующих правил. Единый список правил используется также для распознавания лимитеров телеметрией.

**Ограничения исторической реализации.** Счётчики HTTP-лимитеров находились в памяти процесса, общая MongoDB-политика не делала бюджеты распределёнными. При недоступности базы использовалась последняя известная политика, первоначально выключенная. Это поведение необходимо учитывать при оценке защиты от злоупотреблений. Переключатель не управлял Nginx test gate, ограничениями Socket.IO или внешним прокси.

**Проверено чтением 24.11.2026.** Сервис ревизий и динамический middleware сохранились, но политика расширена полями CAPTCHA и закрытия регистрации, появились дополнительные квоты. Глобальный лимитер теперь выбирает бюджет аккаунта по `requestPrincipal`, а не по историческому списку маршрутов чтения. Для изменений антиспама нужно читать текущий код, прежнюю модель переключателя нельзя считать полной.

**Предотвращение повторов.** Проверять реальный маршрут с исчерпанным бюджетом, отключение и повторное включение, заголовки `Retry-After` и `X-RateLimit-Limiter`, права администратора и доступ к переключателю после блокировки IP. Проверка с `NODE_ENV=test`, где лимитеры пропускаются, сама по себе недостаточна. Исторические тесты включали режим development и отдельную MongoDB.

## Закрепление и пагинация — #117 и последующее уточнение

Исторически выбрали один закреплённый пост в профиле, один в сообществе и отдельный один пост в общей вкладке «Все записи». Выбор хранится в `User.pinnedPost`, `Community.pinnedPost` и `FeedSettings.pinnedPost` соответственно.

Права профиля проверяются по владельцу. В сообществе исторически использовали роль редактора и выше. Для общей ленты администратор может выбрать собственную общедоступную запись или запись сообщества, которым владеет. Проверка на сервере обязательна даже при скрытой кнопке в UI. Приватные записи не должны становиться публичными из-за закрепления.

Файлы — `apps/api/src/controllers/postController.ts`, `userController.ts`, `communityController.ts`, модели `User.ts`, `Community.ts`, `FeedSettings.ts`, компоненты `PostList.tsx`, `PostCard.tsx`, страница `FeedPage.tsx`.

**Неочевидный случай.** Закреплённая запись занимает место первой страницы и исключается из обычной выборки всех последующих страниц. При `limit=1` первая страница может содержать только закрепление, поэтому следующий курсор нельзя брать из пустого массива обычных записей. Исторически использовали верхний ObjectId-маркер `ffffffffffffffffffffffff`. Тест проверял этот сценарий и отсутствие повтора закрепления.

Проверки покрыли отклонение чужого закрепления, закрепление владельцем сообщества и глобальное закрепление администратором. Изменение закрепления во время уже открытой многостраничной выборки требует отдельной оценки. В чате не доказана стабильность такого сценария.

**Проверено чтением 24.11.2026.** Три области хранения и алгоритм первой страницы сохранились. Текущий handoff сообщает о последующем добавлении глобального закрепления со страницы профиля по #156, поэтому прежний набор UI-точек входа уже неполон.

## Онлайн, сообщения и нестабильные курсоры — #118

Индикатор статуса зависит от realtime-сервиса. Онлайном считалось наличие хотя бы одного сокета пользователя, включая фоновую вкладку. Это отличается от видимой активной вкладки, используемой для подавления push-уведомлений. Нельзя подменять одну семантику другой.

Внутренний API realtime принимал до 50 ID за запрос. Массовый запрос списка друзей без разбиения нарушил бы этот контракт, поэтому `onlineUsers` разбивает ID на партии. Данные онлайн добавлялись в DTO поиска, друзей и переписок. В открытом диалоге используются события присутствия, для списка переписок — периодическое чтение сервера раз в 30 секунд.

Файлы — `apps/api/src/services/realtime.ts`, `apps/realtime/src/server.ts`, контроллеры `relationshipController.ts`, `searchController.ts`, `messageController.ts`, `apps/web/src/lib/realtime.ts`, `hooks/useMessages.ts`, `pages/MessagesPage.tsx`.

**Недостаток исторического решения.** Для сортировки всех друзей онлайн первыми агент загружал весь список, сортировал по текущему онлайну и искал позицию предыдущего курсора в новом порядке. При смене статуса между запросами это может пропускать или повторять пользователей. Дедупликация в UI убирает повтор, но не восстанавливает пропущенную строку. Кроме того, загрузка полного списка на каждой странице повышает стоимость запроса.

Полный прогон выявил ещё одну регрессию — после изменения алгоритма перестала вызываться проверка формата курсора друзей, некорректное значение возвращало `200`. Проверку вернули до обращения к данным. При исчезновении строки курсора из списка убрали молчаливый возврат к началу.

**Проверено чтением 24.11.2026.** В текущем `relationshipController.ts` постраничный список снова использует стабильный порядок дружбы, а онлайн-сортировка применяется к непостраничному preview. В поиске людей теперь есть `PeopleSearchSnapshot` со сроком 30 минут и курсором снимка. Это более поздние решения, их реализация и происхождение не разбирались полностью. Исторический подход со свежей онлайн-сортировкой каждой страницы не следует переносить в новый код.

Универсальное отображение статуса осталось незавершённым к концу чата. Позже пользователь убрал дублирование статуса под именем в ЛС, оставив подпись рядом с именем. Сейчас `Avatar.tsx` и `ProfileAvatar` используют `useProfilePresence` и `trackOnline`, поэтому перечень оставшихся поверхностей требуется составить заново по текущему UI. Поле присутствия открытого диалога, его возможное устаревание и fallback на HTTP следует проверять при обрыве сокета.

## Редактирование в первые пять минут — #120

Переиспользован редактор записей сообществ для текста, фотографий и музыки личной записи. Срок для личной записи отсчитывается от `createdAt`, право имеет автор. Права редактирования сообщества проверяются отдельно.

Срок проверяется и перед подготовкой операции, и в условии атомарного обновления MongoDB. Дополнительно сравнивается `updatedAt`, чтобы не перезаписать конкурентную правку. Клиентский таймер служит отображению доступности кнопки. Открытие редактора до окончания срока не даёт права сохранить после срока.

Файлы — `apps/api/src/controllers/postController.ts`, `packages/shared/src/index.ts`, `apps/web/src/components/CommunityPostEditor.tsx`, `PostCard.tsx`. Проверки длины текста должны соответствовать типу записи. Для личной публикации нельзя принимать параметр скрытия автора сообщества.

**Ошибка тестирования агента.** Пограничный тест сначала менял `createdAt` через Mongoose `updateOne`. Поле времени создания оказалось неизменяемым этим способом, поэтому тест ошибочно ожидал запрет для фактически свежей записи. Для исторического тестового документа использовали `Post.collection.updateOne` в отдельной тестовой базе. Нельзя ослаблять production-проверку срока из-за такого ложного результата фикстуры.

## Скрытие публикаций в ленте — #122

Настройки хранятся в аккаунте как множества ID `mutedUsers` и `mutedCommunities`. Добавление и удаление через `$addToSet`/`$pull` делают повторные запросы идемпотентными. Фильтр применяется на API к ленте до пагинации. Прямой просмотр профиля, сообщества и записи сохраняется, на их страницах доступен возврат публикаций.

**Исправленная ошибка требований.** Сначала фильтр скрытого пользователя исключал также его записи в группах. Пользователь уточнил независимость источников. Правильная семантика — скрытие пользователя касается личных публикаций, скрытие сообщества касается публикаций этого сообщества независимо от автора. В меню записи группы не должно быть действия скрытия автора.

Репост другом скрытого источника должен сохраняться. Первоначальная попытка исключить вообще все репосты из фильтра была избыточной — так сохранились бы и собственные репосты скрытого автора. Фильтрация должна учитывать автора и сообщество текущей записи, не рекурсивно исключать цитируемый оригинал.

Файлы — `apps/api/src/controllers/feedMuteController.ts`, `postController.ts`, `models/User.ts`, `apps/web/src/components/FeedMuteButton.tsx`, `PostCard.tsx`, страницы профиля и сообщества. Проверки включали независимость аккаунтов, сохранение записи группы при скрытом авторе, сохранение чужого репоста и отмену скрытия.

**Проверено чтением 24.11.2026.** Разделение личных и групповых источников сохраняется. В `feedMuteController.ts` позже добавлен список скрытых пользователей. Меню карточки теперь рендерится через портал, поэтому прежнее размещение выпадающего блока внутри карточки нельзя считать актуальным.

## Опыт проверки и собственные ошибки процесса

- Агент несколько раз завершал ход с незавершёнными задачами #110, #117 и #118 без конкретного блокера, хотя доступные действия позволяли продолжить. Пользователь отдельно потребовал продолжения. Для следующих агентов сложность реализации и необходимость анализа не являются достаточным основанием передавать работу обратно владельцу.
- Первоначально был выбран неверный репозиторий `wAsOne/Smile`, откуда GitHub вернул `404`. Реальный origin этого проекта — Bubble. При отсутствии доступа нужно сначала проверить локальный remote и не переносить предположения из навыка другого проекта.
- При Git `dubious ownership` использовали разовый `git -c safe.directory=...` для чтения текущего репозитория. Глобальную настройку доверия менять не потребовалось. В конце пользователь явно ограничил Git чтением и работу текущей веткой.
- Точечные тесты долго создавали впечатление готовности. Полный прогон позже нашёл регрессию курсора и несовместимые ожидания DTO в unit-тестах друзей и поиска. Новый `online: false` требовал обновления ожиданий. Неполная фикстура без вычисленного `friendshipAt` также давала искусственный `500` после добавления сортировки. Исправлять нужно контракт и фикстуру по отдельности.
- Новые интеграционные фикстуры создавали дополнительные связи дружбы и сообщества, влияя на последующие тесты. Проявились неверный ожидаемый счётчик друзей и отказ создания сообщества. Добавили очистку данных конкретного сценария. Разделяемая база тестового suite требует явного владения фикстурами.
- Параллельные проверки и автоматическое создание большого числа индексов MongoDB давали таймауты hooks и `MongoNetworkTimeoutError`. В тесте связей отключили `autoCreate`/`autoIndex`, оставив необходимое явное создание индекса. Повторяли проверки последовательно. Первопричина всех таймаутов однозначно не доказана, но журналы показывали ожидание одновременных index builds. Таймауты нельзя объявлять дефектом функций без диагностики.
- Тест шлюза превысил стандартные пять секунд, затем прошёл с увеличенным `testTimeout`. Проверки проводились на отдельных случайно названных localhost-базах, создававшихся только для теста. Настроенная база приложения не использовалась.
- Удаление временной MongoDB сначала предприняли до остановки процесса после неудачного `Get-CimInstance`, получив ошибки занятых файлов. Исправленный порядок — проверить путь исполняемого файла своего процесса, остановить его, проверить абсолютный путь scratch-каталога и затем удалять. Нельзя продолжать разрушительную очистку после сбоя проверки процесса.
- В браузерном тесте ЛС ожидали видимость списка переписок одновременно с открытым диалогом на телефоне. Это неверное ожидание адаптивного UI. Тест разделили на страницу списка и страницу диалога. Для локального Vite с подставленным API требовался `VITE_API_URL=/api`.

## Исторические результаты и оставшаяся неопределённость

К завершению работы 21.11.2026 были выполнены общий TypeScript, сборки API/web/realtime, ESLint, тест Node.js для test gate и 52 сценария `check:site` в Chrome/Edge на 390/1280 px. ESLint сообщил четыре предупреждения в неизменённых файлах. Дополнительные целевые UI-проверки выполнялись с имитацией API, в том числе на 320/768 px.

Первый полный прогон API завершился с пятью ошибками и одним пропуском. После исправлений соответствующие группы тестов повторили успешно. Пропущенный тест настройки шлюза запустили отдельно с тестовым секретом и увеличенным таймаутом. Совокупно эти прогоны покрыли 414 тестов API и 27 realtime. Это исторические результаты нескольких запусков, а не один новый полностью зелёный прогон текущего checkout.

На конец чата оставались ручная проверка исходного Safari/iPhone-дефекта, расширение индикаторов онлайн на остальные места и оценка поведения изменяющегося онлайн-порядка между страницами. Текущие файлы уже содержат последующие решения для части этих вопросов, поэтому открытые задачи нужно сверять заново. Работа реального Socket.IO, доставки писем, внешнего S3 и состояния развёрнутых версий не устанавливается тестами с имитацией API.

Комментарии тестировщикам публиковались в #110–118, #120 и #122. По решению владельца из них удалили фразы о рабочей ветке и необходимости установки стенда — задачи передаются тестировщикам после выкладки на их ветку. Сами комментарии не являются доказательством деплоя или закрытия проверки.

Для предотвращения повторов следует проверять штатные точки входа и права, API до и после изменения формата, старые документы, повторные и конкурентные операции, предел окна редактирования, `limit=1`, удаление строки курсора, недоступный оригинал репоста, изменение онлайн-статуса между страницами и реальную grid-ячейку текста. Готовность отчёта должна ограничиваться фактически выполненными проверками и точной версией кода.
