## Первопричина дублирования публичных ID

**Подтверждено исходным кодом и diff коммита.** До исправления `apps/api/src/services/authService.ts` использовал запрос следующего вида:

```ts
User.findOne({ email: input.email })
  .or([{ username: input.username }])
  .collation({ locale: "en", strength: 2 });
```

Условие `email` осталось самостоятельным обязательным условием, а `.or()` добавил отдельную группу условий. Запрос фактически требовал совпадения почты вместе с ником. Новый адрес почты позволял пройти предварительную проверку занятого `username`.

В модели `apps/api/src/models/User.ts` уже был объявлен уникальный индекс `username` без учёта регистра. Объявление индекса в Mongoose само по себе не доказывает, что индекс успешно создан в существующей базе. Старые дубликаты способны помешать построению такого индекса.

**Предположение о production.** Отсутствующий или неработающий ожидаемый индекс мог объяснять, почему ошибка предварительной проверки привела к реальным дублям. Состояние индексов live не проверялось, поэтому конкретная причина отсутствия защиты БД не установлена.

## Внутренний ID, публичный ID и последствия дублей

**Подтверждено кодом.** У каждого аккаунта есть MongoDB `_id` типа `ObjectId`. Поле `username` задаёт публичный ID и адрес `/u/:username`. Эти идентификаторы выполняют разные функции.

- `apps/api/src/models/Post.ts` хранит автора как ссылку `ObjectId` на `User`.
- `apps/api/src/utils/serializers.ts` выдаёт внутренний `_id` строкой в поле `id`.
- `apps/api/src/controllers/userController.ts`, функция `findByUsername`, использует `findOne` по публичному ID с collation `en`, strength 2. При дублях такой адрес не позволяет однозначно выбрать аккаунт.
- Маршрут `/moderation/users/:id/measures` в `apps/api/src/routes/index.ts` применяет меры по внутреннему ID.

**Сообщено пользователем.** Два аккаунта повторили его публичный ID, публиковали посты, а ссылки на их профили открывали профиль администратора. Ограничение публикаций для этих аккаунтов сработало, при этом администратор сохранил возможность публиковать. Это согласуется с привязкой мер к `_id`.

Блокировка или запрет публикаций не освобождают `username` и не устраняют неоднозначность ссылок. При работе со старыми дублями аккаунты нужно различать по внутренним ID. Исторический совет агента о риске бана по нику следует применять к конкретному маршруту: административные действия по публичному имени и меры модерации по `_id` имеют разную адресацию.

## Итоговая защита регистрации

**Подтверждено текущим кодом.** В `authService.register` занятость `username` и почты проверяется отдельно. Проверка ID обращается ко всем аккаунтам с collation `{ locale: "en", strength: 2 }`. Поэтому `wAs`, `was` и `WAS` считаются занятым одним публичным ID независимо от почты и признака защиты записи.

Для конкурентных регистраций принят частичный уникальный индекс `unique_registered_username` в `apps/api/src/models/User.ts`:

```ts
keys: { username: 1, registrationUsernameProtected: 1 }
unique: true
collation: { locale: "en", strength: 2 }
partialFilterExpression: { registrationUsernameProtected: true }
```

Новые аккаунты по почте и Google получают `registrationUsernameProtected: true`. Старые записи без этого флага не мешают построению частичного индекса. Их ID при этом учитываются предварительной проверкой. Такое сочетание позволяет оставить регистрацию свободных ID открытой при наличии старых дублей.

`ensureRegistrationUsernameIndex()` ожидается перед созданием аккаунта. Promise создания индекса сохраняется в процессе, а при ошибке сбрасывается для следующей попытки. Это объединяет параллельные попытки создания индекса внутри процесса. Уникальность конкурентных вставок обеспечивает MongoDB. Глобальный уникальный индекс `username` также остался объявлен в модели.

Ошибки MongoDB `11000` распознаются по `keyPattern` и переводятся в `409` с отдельными сообщениями о занятом ID или почте. Предварительная проверка без индекса не закрывает гонку между проверкой и вставкой.

Создание нового Google-аккаунта вынесено в `createGoogleAccount`. Оно использует ту же проверку старых ID и тот же индекс. При конкурентном захвате кандидата генерируется следующий вариант, максимум семь попыток. Нормализованная основа ограничена 16 символами, случайный суффикс занимает восемь символов, что укладывается в предел публичного ID 24 символа.

## Управляемая пауза регистрации

**Подтверждено текущим кодом.** Настройка `registrationClosed` добавлена в существующий документ настроек лимитов MongoDB. Отсутствующее поле трактуется как `false`, поэтому старые установки по умолчанию сохраняют открытую регистрацию.

Связанные файлы и контракты:

- `apps/api/src/models/RateLimitSettings.ts` — сохранённое поле.
- `apps/api/src/services/rateLimitSettings.ts` — чтение, сохранение и `assertRegistrationOpen`.
- `apps/api/src/controllers/rateLimitController.ts` и `apps/api/src/routes/index.ts` — `GET/PUT /admin/registration`, доступные администратору, тело `{ registrationClosed: boolean }`.
- `apps/api/src/controllers/authController.ts` — проверка паузы до капчи и регистрации по почте, а также при выдаче капчи.
- `apps/api/src/services/authService.ts` — проверка перед созданием нового аккаунта Google. Возвращающиеся Google-пользователи и связывание существующего аккаунта проходят через прежние ветки входа.
- `apps/web/src/components/RegistrationSettings.tsx`, `apps/web/src/pages/ModerationPage.tsx` — вкладка «Регистрация» в панели модерации.
- `apps/web/src/components/AuthForm.tsx`, `apps/web/src/lib/api.ts` — сообщение «Регистрация на сайте временно недоступна» и скрытие формы при ответе о паузе.

Пауза возвращает `503` с серверным сообщением `Registration is temporarily unavailable`. Форма отличает его через `ApiError.serverMessage`. Занятый ID возвращает `409` и сообщение «Этот ID профиля уже занят».

Неочевидная зависимость — гостевая форма узнаёт о паузе через запрос выдачи капчи, даже когда сама капча выключена. Проверка на сервере регистрации нужна и для уже открытой формы. Прямое чтение настроек в этих путях отличается от пятисекундного кэша `rateLimitPolicy`, используемого лимитерами. Пауза создания аккаунтов допускает вход существующих пользователей и подтверждение ранее созданных аккаунтов.

## Ошибки агента и отвергнутые подходы

1. **Избыточная блокировка регистрации в первом хотфиксе.** Агент добавил обязательную проверку существования глобального уникального индекса и `503` при его отсутствии. Старые дубли могли не дать создать индекс, из-за чего закрывалась регистрация любых новых людей. Это было следствием выбранного решения, а не обязательным требованием проекта. Подход заменён частичным индексом для новых записей и проверкой всех старых ID.
2. **Слишком жёсткий порядок исправления live.** Первоначально агент представлял разбор/переименование старых дублей как предварительное условие выпуска. Итоговый вариант снимает эту зависимость для регистрации свободных ID. Переименование старых аккаунтов осталось отдельной задачей для корректных ссылок.
3. **Недостаточное первое доказательство через скриншот.** Первый скриншот формы получен с реальным кодом `register`, но имитацией записи БД и перехватом браузерных запросов. Он подтверждал отображение ошибки, но не проверял MongoDB и конкурентные вставки. Это ограничение было сообщено. Позже проверка повторена с реальным локальным API и отдельной MongoDB.
4. **Преждевременный вывод о недоступности локальной MongoDB.** Отсутствие `mongod` в PATH, стандартном каталоге и работающего Docker не означало отсутствия бинарника. Позже найден отдельный `mongod.exe` во временном каталоге. Его путь был особенностью рабочей машины и не является зависимостью проекта.
5. **Инструментальные сбои.** Запуск временного сценария через `tsx` завершился ошибкой `uv_os_get_passwd`; запуск через существующий Vitest сработал. Стандартный Chromium Playwright отсутствовал, для проверки использован установленный Chrome через `executablePath`. Эти обходы не подтверждают работоспособность других браузеров.
6. **Согласованность типов.** Добавление `registrationClosed` в возвращаемую политику сломало TypeScript у существующей заглушки `rateLimitPolicy`. Исправлена заглушка в `apps/api/src/tests/rateLimit.test.ts`. Изменение формы объекта затрагивает и тестовые потребители.

## Открытые ограничения и предотвращение регрессий

**Подтверждённые границы решения.** Старые дубли автоматически не переименовываются. Ссылки по одинаковому `username` остаются неоднозначными до отдельного исправления данных. Наличие/отсутствие этих дублей на live после завершения чата неизвестно.

**Вывод из текущего кода, отдельно не тестировался.** Частичный индекс защищает вставки с флагом `registrationUsernameProtected: true`. Прямые вставки, импорт или иная версия API без флага могут обходить эту защиту. При расширении путей создания аккаунтов необходимо сохранять проверку всех ID, установку флага и ожидание индекса. Работа старой и новой версии API одновременно не проверена.

**Непроверенные эксплуатационные сценарии.** Создание частичного индекса требует прав MongoDB и может добавить задержку первому новому аккаунту на каждом процессе. Ошибка сбрасывает Promise для повтора. Поведение при удалении индекса извне после успешного кэширования, конкурентном занятии почты/Google ID, отключении регистрации в середине уже выполняющегося запроса и восстановлении после сетевой ошибки отдельно не проверялось. Текущий `register` сервиса полагается на проверку паузы в HTTP-контроллере, поэтому новый прямой вызывающий код должен учитывать этот контракт.

Для предотвращения повторения ошибки сохранять проверки по независимым ключам, согласованную collation в запросе и индексе, обработку гонки на вставке и тест базы с уже существующими дублями. Объявленный индекс и реально построенный индекс следует проверять раздельно. Проверка только на чистой базе с глобальным уникальным индексом может скрыть исходную ошибку.
