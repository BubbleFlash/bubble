## 1. Архитектура и общие точки изменений

**Подтверждено исторически.** Монорепозиторий содержит React/Vite-приложение `apps/web`, Express/Mongoose API `apps/api`, отдельный Socket.IO-сервис `apps/realtime` и общие схемы/DTO `packages/shared`. Команды проверки запускаются через npm workspaces.

- `apps/web/src/App.tsx` объединяет оболочку, маршруты и провайдеры. Изменения общих обработчиков здесь распространяются на лениво загружаемые страницы и диалоги.
- Общие элементы `PostCard`, `InlineComments`, `MusicTrackList`, `BrandMark` используются в нескольких представлениях. Исправление одной страницы не доказывает корректность всех потребителей.
- Оформление складывается из `global.css`, `theme.css`, Aero-токенов и правил `aero-home.css`, `aero-components.css`, а также загружаемого страницей `appearance.css`. Причину визуального дефекта нужно искать в итоговом каскаде и computed styles.
- Тема задаёт семантические цвета, например `--aero-color-text`, `--aero-color-canvas`, и стеклянные градиенты. Пользовательская прозрачность меняет заливки через `--aero-window-opacity`.

**Предотвращение регрессий.** Перед правкой общего селектора находить все экземпляры компонента, в том числе в модальных окнах, и проверять более специфичные правила пользовательских настроек.

## 2. Подложка вкладок и закрепление под шапкой

**Подтверждено исторически.** Общий класс `.tabs` используется в поиске и новостях. `.tabs.feed-tabs` также встречается в ленте, друзьях, музыке, сообществах, настройках, модерации и диалогах. Наличие `feed-tabs` не означает, что элемент закрепляется: некоторые экземпляры переопределены в `position: static`.

Первоначально подложка всех групп вкладок стала непрозрачной и использовала `--aero-color-canvas`, независимо от прозрачности окна. После проверки пользователь уточнил требование: подложка нужна только после прилипания вкладок к шапке. До этого, а также у незакрепляемых вкладок, фон прозрачный.

Историческое решение:

- В `apps/web/src/hooks/useStickyTabs.ts` добавлен общий обработчик, подключённый из `App.tsx`.
- Обработчик проверяет computed `position`, вычисленный `top`, положение элемента и наличие прокрутки. Закреплённые вкладки получают `data-stuck="true"`.
- Проверка откладывается через `requestAnimationFrame`, вызывается при прокрутке и изменении размеров окна. `MutationObserver` обнаруживает динамически появившиеся элементы, `ResizeObserver` отслеживает высоту `.aero-window-chrome`.
- `aero-home.css` включает непрозрачную подложку только для этого атрибута. Размытие под вкладками не добавлялось.

**Обнаруженный сбой проверки.** Первый браузерный прогон получил вкладки уже у шапки, но ещё без `data-stuck`. Повторный прогон показал правильное состояние. Это выявило зависимость от асинхронного измерения высоты шапки. Добавили наблюдение за её размером; точная последовательность событий первого сбоя не была доказана.

**Фактическая проверка.** В Chrome при ширинах 390 и 1280 px на настоящей странице с подменённым API и искусственно добавленной высотой проверены прозрачность до прокрутки, непрозрачность после закрепления и возврат прозрачности наверху. Typecheck прошёл.

**Ограничения.** Не проверены все реальные страницы, Firefox/Safari, все вложенные области прокрутки и длинные последовательности переходов. Сравнение `getBoundingClientRect().top` с `top` нуждается в пересмотре, если меняется контейнер прокрутки. Глобальное наблюдение DOM и чтение геометрии не проходили отдельный замер нагрузки. Не копировать этот подход как универсально доказанную реализацию sticky-состояния.

## 3. Прокрутка, iOS и просмотр изображений

**Сообщено пользователем в ранней части истории.** Скрытие полосы прокрутки вызвало горизонтальные скачки центрального контейнера между страницами. Попытки сделать пустую полосу прозрачной привели сначала к чёрной полосе, затем к чёрному фону значительной части страницы. Пользователь выбрал постоянно зарезервированную полосу с невидимым ползунком, когда прокрутка не нужна.

В видимой позднее CSS-версии были `overflow-y: scroll`, `scrollbar-gutter: stable`, стили WebKit scrollbar и `html[data-aero-no-scroll]` для скрытия ползунка. Отдельная ветка `@supports not selector(::-webkit-scrollbar)` задавала Firefox-цвета. **Точная первопричина чёрного фона в доступных инструментах не установлена.** Это нельзя описывать как доказанный дефект конкретного CSS-свойства.

Исторический `docs/PROJECT_HANDOFF.md` дополнительно фиксировал:

- Для #40 и #41 значок уведомлений получил явные размеры, а на мобильной компоновке отключили фиксированный слой обоев, который мог перекрывать контент при pinch zoom. Проверка на физическом iPhone оставалась необходимой.
- Для просмотра изображений восстановили прозрачные зоны перехода слева и справа на всю высоту изображения. В режиме исходного размера оставили компактные кнопки, чтобы зоны не мешали прокрутке.

**Предотвращение регрессий.** Различать документную и внутреннюю прокрутку, фиксированные декоративные слои и визуальный viewport. При изменении галереи проверять клики по краям и режим исходного размера. Desktop-эмуляция мобильного размера не подтверждает поведение iOS при масштабировании.

Связанные задачи: #37, #40, #41, #46; файлы `aero-home.css`, `global.css`, `App.tsx`, `ImageGallery.tsx`.

## 4. Настройки аккаунта и жизненный цикл учётных данных

**Подтверждено исторически.** Формы смены почты, смены пароля и удаления аккаунта в `AccountSettings.tsx` первоначально раскрывались внутри карточки. Пользователь потребовал отдельные модальные окна. Решение использовало нативный `<dialog>.showModal()`, общий `AeroTitlebar` и `useDialogBackdrop`.

- При открытии фокус переходит к первому полю, при закрытии возвращается к вызвавшему элементу, если он ещё существует.
- Escape и жест целиком на подложке закрывают окно. Во время отправки закрытие блокируется.
- Ошибки остаются в форме, несовпадающие пароли проверяются до отправки.
- Смена почты отправляет подтверждение на новый адрес. До подтверждения текущий адрес входа сохраняется.
- После смены пароля сеанс завершается. Удаление скрывает профиль и допускает восстановление входом в течение семи календарных месяцев. По окончании срока данные автора обезличиваются, опубликованные материалы сохраняются.

Последние пункты подтверждались отдельным интеграционным сценарием `accountLifecycle.integration.test.ts` на временной MongoDB. Это историческая проверка, а не гарантия состояния рабочей базы.

**Неочевидная зависимость оформления.** Правило `.aero-home[data-custom-opacity] :is(.aero-panel, .aero-dialog, .music-attachment-picker)` перекрывало стеклянный фон новых окон. Для `account-settings-dialog` потребовалось более специфичное правило стеклянной рамки. Важно проверять окно и при стандартных, и при пользовательских настройках прозрачности.

**Ошибка агента.** В формы добавлена безусловная подсказка про Google, хотя пользователь не планировал подключение этого способа входа. Проверка нашла реализованные `AuthForm`, `GoogleButton`, серверный маршрут и зависимость от `VITE_GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_ID`. Наличие кода не подтверждало включение функции на сервере. По запросу подсказка удалена.

Связанные задачи #59 и #26. Основные исторические файлы: `AccountSettings.tsx`, `SettingsPage.tsx`, `accountService.ts`, `authService.ts`, `accountDeletion.ts`, `AuthToken.ts`, `User.ts`, `serializers.ts`.

## 5. Письма, бренд и кэширование ресурсов

**Подтверждено исторически.** Все девять видов писем сведены к общему шаблону `apps/api/src/services/emailTemplates.ts`: подтверждение почты, восстановление пароля, подтверждение смены почты, уведомление об изменении почты, смена пароля, скрытие и восстановление аккаунта, обратная связь и служебные ошибки.

- HTML использует таблицы и сплошные цветовые fallback-заливки для почтовых клиентов, одновременно формируется текстовая версия. Динамический текст HTML экранируется.
- Логотип и Coiny подключены абсолютными URL. Историческая реализация выбирала базу из `process.env.CLIENT_ORIGIN`, затем origin ссылки действия, затем localhost. Для реальных писем критична правильная публичная конфигурация адреса сайта.
- Реальная отправка была через Resend. При отсутствии ключа письмо выводилось в журнал разработки, в production отправка пропускалась с предупреждением. Самостоятельный почтовый сервер тогда оставался идеей бэклога.
- Команда `npm run preview:mail -w @commune/api` собирает примеры в `dist/mail-preview`. Скрипт копирует логотип и шрифт рядом с HTML и заменяет внешние URL этих ресурсов локальными, чтобы просмотр не зависел от запущенного сайта.
- Поддержка `@font-face` почтовыми клиентами не гарантирована, нужен читаемый запасной шрифт. В браузере проверялась загрузка ресурсов, реальная доставка и отображение во всех почтовых клиентах не проверялись.

Логотип сайта проходит через `BrandMark.tsx`, но favicon, Apple touch icon, manifest, offline-страница, push и письма имеют отдельные ссылки. Простая замена компонента не обновляет весь бренд. При изменениях использовали новые имена файлов и повышали версию service worker, чтобы избежать старого кэша.

Историческое окончательное соответствие: квадратный исходник `BubbleLogoSquare2.png` экспортирован в ресурсы `*-v3.png`; `BubbleLogoSquare3.png` — в `*-v4.png`. Это номера экспортов, не номера исходного дизайна. Пользователь несколько раз сравнивал варианты и окончательно вернул второй исходник. При подготовке к слиянию неиспользуемые варианты удалены, добавлен `fonts/Coiny-OFL.txt`.

Связанные задачи #57, #60; также `BrandMark.tsx`, `index.html`, `manifest.webmanifest`, `offline.html`, `sw.js`, `previewMail.ts`. Не переносить исторические имена экспортов в новую ветку без проверки ссылок.

## 6. Неудачные попытки CSS и критерии качества

**Непосредственно наблюдалось.** Градиентная надпись через `background-clip: text` и прозрачную заливку текста выглядела серой при наложении `text-shadow`. Удаление text-shadow и использование drop-shadow сделали цвет насыщеннее, но последующие варианты с выраженной обводкой пользователь всё равно отверг как слишком тёмные и недостаточно похожие на образец.

Причина серого оттенка от перекрывающих теней была рабочим объяснением агента, а не изолированным тестом механизма рендеринга. Факт — визуально неудачные варианты и обратная связь пользователя.

Принятое в итоге требование: настоящий HTML-текст, существующий Coiny, основной тёмно-синий семантический цвет сайта и деликатные светлые блики. Никаких новых изображений текста или изменения исходника иконки.

**Ошибка процесса.** Агент неоднократно называл оформление завершённым после проверки computed styles и отсутствия пересечений. Эти проверки подтверждали геометрию, но не сходство с референсом. Для такой задачи нужен визуальный просмотр при масштабе 100% и отдельная оценка результата пользователем.

Долгосрочный вывод: минимальная правка по токенам часто надёжнее серии независимых теней, градиентов и обводок. Геометрия шапки, поиск и уведомления — отдельные ограничения, их нельзя менять ради декоративного эффекта.

## 7. Производительность: что известно, а что нельзя обещать

Ранний этап #3, #44, #58 частично отсутствует в журнале чата. Прочитанный исторический handoff сообщал следующие решения:

- Время воспроизведения вынесено из общего музыкального контекста, чтобы `timeupdate` не перерисовывал списки вложенных треков.
- Использованы общие строки музыки и пакетные статусы принадлежности библиотеке вместо запроса на каждый трек.
- Отложена загрузка части медиаданных вне viewport, добавлены компоненты `AssetImage`/`useNearViewport` и обработка fallback-загрузки.
- Работа с изображениями учитывала сжатие и сохранение GIF/альфа-канала. Отдельно проверялся отказ прямого URL хранилища с возвратом к API.
- Стенд `tools/measure-feed.mjs` и `apps/web/perf-harness.jsx` использовал подменённые API и Audio. Такой стенд проверяет выбранную нагрузку, а не реальную сеть, декодирование всех файлов или слабое устройство.

Точные цифры и условия следует брать из `docs/PERFORMANCE.md` соответствующей ревизии. Они не доказывают ускорение каждого браузера: в старых замерах часть метрик улучшалась, часть ухудшалась.

**Браузерные ограничения.** Playwright Chromium по умолчанию не запускался из-за отсутствующего bundled headless shell. Для Chrome использовался установленный `chrome.exe`. Попытка управлять обычным Firefox через Playwright завершалась ошибкой запуска, headless CLI-попытка тоже не дала подтверждённой визуальной проверки. Успех Chrome не следует объявлять проверкой Firefox или Safari.

## 8. Проверки, Git и подготовка к слиянию

**Подтверждено исторически.** Ветка этапа имела базу `1a139af8da28a6d14ed7489fa88a65e03bd7dd54`. Перед передачей сравнение `git ls-remote` показало тот же SHA у удалённой `develop`. Позднее при разборе Trello код читался через GitHub на `982803fcb60fb61cc6058b0d1ab4e9aeb28e30d1`. Эти SHA — точки сравнения, не коммиты, созданные агентом.

Пользователь разрешал менять код только в текущей ветке и использовать Git исключительно для чтения. Коммиты, переключение веток, push, merge и deploy в этой работе агент не выполнял. Изменённые файлы включали незарегистрированные файлы, поэтому один `git diff --stat` давал неполный состав результата.

- Ошибка ownership Git обходилась параметром одного вызова `git -c safe.directory=...`, без записи глобальной конфигурации.
- `npm run typecheck` и `npm run build` для workspace-пакетов прошли. `git diff --check`, синтаксис `sw.js` и ссылки manifest проверены.
- Основной запуск тестов дал API 361 passed / 24 skipped и realtime 24 passed. Пропущенные интеграционные сценарии затем выполнены отдельно: 18 для аккаунта/репостов/модерации и 6 для связей. Исторический итог — 409 прошедших тестов, а не один запуск с таким счётчиком.
- Vite предупреждал о большом чанке выбора эмодзи. Предупреждение не устранялось в рамках подготовки.

**Изоляция MongoDB.** Docker был недоступен текущему процессу. Найден существующий `mongod.exe`, запущен отдельный экземпляр с временным dbpath и случайной тестовой БД. Остановка происходила в `finally`.

Первая проверка готовности через `Get-NetTCPConnection` не нашла listener; следующая попытка использовала сообщение `Waiting for connections` в журнале. Стандартный порт 27017 был занят. Для `relationships.integration.test.ts` добавили `BUBBLE_RELATIONSHIPS_TEST_MONGO_PORT` с валидацией и сохранили прежний opt-in. Существующий процесс MongoDB не останавливали.

**Практика.** Запускать интеграционные тесты явно, проверять владельца тестовой БД перед её удалением и не интерпретировать skipped как passed. При отсутствии bundled браузера или Docker сначала искать доступный штатный инструмент, а не менять production.

## 9. Ошибки агента в инструментах и отчётности

- Слишком широкий вывод Trello JSON с полными описаниями был обрезан. Затем отдельно извлечены список карточек и нужные фрагменты. Полноту данных нужно проверять до вывода результатов.
- В PowerShell использована shell-конструкция с `{AccountSettings,...}.tsx`, которая дала ошибку парсинга. Исправлено перечислением путей.
