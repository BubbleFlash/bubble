## 1. Прозрачная оболочка и прокрутка — #80

**Сообщено пользователем.** При прокрутке текст был виден через прозрачную верхнюю рамку. Последовательные исправления давали непрозрачное белое пятно, тёмные линии по краям, затем горизонтальные швы. Одновременно на мобильном экране список личных сообщений выходил за доступную ширину. Возврат к прежнему варианту не устранил обе проблемы. После исправления ленты тот же дефект обнаружился в профиле.

**Ошибка агента.** Несколько промежуточных вариантов были переданы без достаточной проверки соседних страниц и мобильных ЛС. Типичный скрин ленты оказался недостаточным критерием готовности общего layout. Точный CSS каждого неудачного варианта недоступен, поэтому приписывать ему конкретный stacking context или браузерный баг нельзя.

**Историческое решение, подтверждено чтением текущего кода.** В `apps/web/src/App.tsx` измеряется пересечение нижней границы chrome и содержимого `.aero-window > .shell`. Содержимое обрезается через `clipPath` с округлением верхнего inset вверх. Обработчики scroll/resize планируют измерение через requestAnimationFrame; ResizeObserver отслеживает размеры. Очистка отключает подписки, кадр и inline-стиль. Решение применяется в общей оболочке, а не отдельно в ленте.

**Причина выбора.** Требовалось скрыть проходящий за шапкой контент, сохранив прозрачность декоративной рамки. Добавление непрозрачной маски меняло сам эффект оформления. Расширять clipping на внутренние контейнеры без проверки опасно для сетки ЛС, теней и выступающих элементов.

**Предотвращение повторения.** Проверять длинную и короткую страницу, профиль, настройки, события, список диалогов и открытую переписку на узкой ширине. Проверять переход между ними без перезагрузки. Учитывать дробные координаты и изменение высоты chrome. Текущий `App.tsx` уже содержит дополнительные изменения прокрутки для Android Firefox из последующих работ; переносить исторический вариант целиком поверх него нельзя.

## 2. Ограничения текста, редактор и сворачивание — #93, #102

**Требование.** Лимит увеличен до 2 000 символов для личных и групповых записей, репостов и сообщений, до 1 000 для комментариев. Лимит записей одинаков для обычного аккаунта и Plus. Историческое преимущество Plus «более длинные записи» убрано.

**Зависимость.** Менять нужно согласованно Zod-схемы и DTO в `packages/shared/src/index.ts`, ограничения Mongoose в `apps/api/src/models/{Post,Comment,Message}.ts`, потребителей этих лимитов и описание Plus. Изменение только счётчика или maxlength не меняет серверный контракт. Названия констант сами по себе не доказывают различие тарифов. Указанные значения по-прежнему присутствуют в shared при текущей сверке.

**Сообщено пользователем.** В длинном сообщении с эмодзи курсор визуально расходился с набираемым текстом. **Историческая диагностика по handoff.** В `apps/web/src/pages/MessagesPage.tsx` синхронизированы визуальный слой и поле ввода: высота строки, ширина с учётом полосы прокрутки и scroll offset. Эта причина описана в истории, но первоначальный воспроизводящий DOM и полный дифф недоступны. Для редакторов с наложенным слоем проверять все три величины совместно, особенно при появлении scrollbar.

**Решение #102, подтверждено исходником.** `apps/web/src/components/PostText.tsx` сворачивает текст после 700 символов либо десяти строк. Длина в символах не заменяет измерение высоты: короткий текст может содержать много переводов строки. Компонент измеряет скрытый элемент с теми же стилями и подбирает префикс двоичным поиском, оставляя место встроенной ссылке раскрытия. Пересчёт выполняется при изменении ширины и завершении загрузки шрифтов; наблюдатели очищаются.

**Пограничные случаи.** Ссылку нельзя разрывать в середине URL, иначе изменятся текст и цель перехода. `Array.from` сохраняет Unicode code points, но сам по себе не гарантирует целостность составной emoji-графемы. Проверка полного диапазона графем в доступной истории не доказана. Полная страница записи должна показывать весь текст; карточки и репосты используют одинаковое раскрытие. Проверять смену пользовательского шрифта, узкую ширину, длинный URL, множество переносов и кнопки «Читать далее»/«Свернуть» внутри текста.

## 3. Прочтение уведомлений связано с навигацией — #84

**Требование.** Обычная ЛКМ по событию открывает цель в текущей вкладке и отмечает прочитанным только выбранное событие. Ctrl/Cmd-клик и другие штатные способы открытия ссылки должны продолжать работать. Правило относится и к колокольчику, и к странице событий.

**Скрытая зависимость.** Общая сессия просмотра ранее помечала показанные события прочитанными при уходе со страницы или закрытии меню. Сам переход по ссылке запускает такой уход и может непреднамеренно прочитать весь набор. Поэтому недостаточно заменить `target` ссылки: нужно согласовать выбранный элемент с обработчиком завершения просмотра.

**Историческое решение.** В `App.tsx`, `components/NotificationList.tsx`, `components/NotificationMenu.tsx`, `pages/NotificationsPage.tsx` обычная навигация вызывает `onNavigateToItem`, сбрасывающий накопленный набор через `finish([])`, и отдельно отмечает выбранную запись с `{ id, createdAt }`. Обычный уход без выбора сохранял массовое прочтение показанного. В текущих файлах эти точки связи остаются; за точным серверным контрактом чтения нужно обращаться к текущему коду, который менялся позднее.

**Предотвращение.** Проверять минимум два непрочитанных события, переход по одному, закрытие меню без выбора, уход на другую страницу и открытие в новой вкладке. Не считать «одна запись визуально выбрана» доказательством единственного ID в запросе.

## 4. Успешный ответ API может быть пустым — #59

**Подтверждено исторически.** Смена почты возвращала успешный `202` с пустым телом. Безусловный `res.json()` превращал успех в клиентскую ошибку. Проверка только `204` также не решает случай `202`.

**Решение.** `apps/web/src/lib/api.ts` читает успешный ответ через `res.text()` и разбирает JSON только для непустого тела. При объединении с сетевой веткой сохранена `assertSessionGeneration(generation)` после чтения тела, чтобы ответ прежнего аккаунта не попал в новое состояние сеанса. Этот порядок присутствует и сейчас.

**Ошибки для пользователя.** Конфликт регистрации не должен показываться только как код HTTP 409. Осмысленные переводы берутся из серверного сообщения и контекста операции. В `components/AuthForm.tsx` согласована фраза «Пароль должен содержать минимум 8 символов». Фактический контракт shared по-прежнему ограничивает пароль сверху 128 символами; сокращение текста не отменяло серверный максимум. Исчерпывающий актуальный словарь ошибок следует читать в `lib/api.ts`, он менялся после этого чата.

**Открытая проверка.** Реальная доставка писем восстановления и подтверждения почты в целевом окружении не была доказана доступными результатами. Отдельный экран GitHub device authorization из разговора относился к авторизации инструментов и не подтверждает работу восстановления Bubble.

## 5. Скрытый автор и 18+ имеют разные границы защиты — #82, #105

**Требование #82.** Можно скрыть автора записи сообщества от обычных читателей. Сам автор, сотрудники Bubble и уполномоченные управляющие сообщества должны видеть личность вместе с отметкой, что она скрыта. Нельзя скрыть только подпись в React и продолжать выдавать автора гостю в JSON.

**Историческое решение.** Контроль реализован в сериализации записи и репоста. Скрытые публикации исключались из чужого профиля и ленты подписок, поскольку сам выбор этих записей мог раскрыть личность. Проверять нужно прямую запись, репост, публичный API, профиль и подписки, а не только карточку сообщества.

**Текущая сверка.** В `apps/api/src/utils/serializers.ts` и `services/repostService.ts` остаются `hideAuthor` и проверки зрителя. В репостах видны исключения для автора, admin/moderator и роли сообщества не ниже editor. Полная матрица авторизации текущего checkout сейчас не прогонялась. Исторические интеграционные проверки ролей описаны в handoff.

**Требование #105.** Метка закрывает только фотографии серой размытой плашкой. Текст записи виден; нажатие в любой точке плашки раскрывает фото. Это добровольное раскрытие изображения, а не возрастная проверка или серверный запрет на получение файла.

**Ошибка настройки.** Сначала пользователь различал почти всё на изображении, затем усиленный вариант скрывал его полностью. Объективной универсальной величины blur из этого не следует. Важнее не дать открыть просмотрщик сквозь плашку или фокусировать скрытую галерею. Текущий `components/PostImages.tsx` использует `inert`, `aria-hidden` и отдельную кнопку поверх галереи. Проверять карточки, репосты, клавиатуру и сенсорное раскрытие. Старые записи без новых флагов должны сохранять прежнее поведение.

## 6. Пагинация музыки и тесты потребителей — #103

**Историческая проблема.** Библиотека обрезалась лимитом первой страницы. В `pages/MusicPage.tsx` добавлена infinite query с существующим курсорным `/music/picker`, страницами по 50, `nextCursor`, дедупликацией по ID и догрузкой. Старый формат `/music` сохранён ради его потребителей. Связанные файлы — `apps/api/src/services/musicService.ts` и `tests/musicPagination.integration.test.ts`.

**Подтверждённая ошибка интеграции при слиянии.** Тест из develop подменял `/api/music?...`; новая страница вызывала `/api/music/picker`. В первом браузерном прогоне четырежды получено `Expected 2, Received 0`: счётчик перехваченных запросов был нулевым, а интерфейс показывал 404 отсутствующей fixture. Это свидетельствовало о несовпадении тестового контракта, а не об отсутствии retry в API.

**Исправление.** В `tools/site-checks/candidate.spec.ts` обновлены путь перехвата, форма ответа `{ tracks, nextCursor }` и точная проверка alert библиотеки. После этого все 52 сценария прошли. Перед изменением рабочей сетевой логики нужно сначала сверить URL, payload и обработчик fixture.

**Ограничение свидетельств.** Пользователь разрешил загрузить тестовые треки в конкретный аккаунт локального сервера. Доступная история не содержит полного журнала этой загрузки, поэтому наличие и дальнейшую очистку этих данных нельзя считать подтверждёнными.

## 7. Публичная главная, дневник и команда — #66, #77, #107

**Архитектурное решение.** Гостевая главная стала страницей о проекте с входом и регистрацией. `pages/SiteInfoPage.tsx` используется также для `/about`, `/rules` и форм восстановления/подтверждения учётных данных. Для вошедшего пользователя страницы проекта используют публичную оболочку с возвратом на сайт. Основная лента остаётся домашней страницей вошедшего пользователя.

**Неочевидная связь.** `index.html` выполняет ранние запросы до React. После замены гостевой ленты нельзя продолжать автоматически запрашивать `/public/posts` на главной. При слиянии сохранён `/site-content` для гостевых `/`, `/explore`, `/about`, а ранний refresh удалён ради сериализации сеанса из сетевой ветки. Изменение маршрута требует проверки HTML prefetch, оболочки и тестов доступности.

**Ошибка интеграции.** `tools/site-checks/reachability.spec.ts` ждал старую ленту и заголовок, которые новая главная больше не выводила. Проверка адаптирована: ждать данные проекта и входную форму, а работоспособность публичного API ленты проверять отдельным запросом. Локально сценарий прогнан на preview с имитацией API. Доступность реального развёрнутого сайта таким результатом не установлена.

**Публичный кэш и сеанс.** Безусловный `qc.clear()` при подтверждении гостя удалял уже запущенные публичные запросы. В `store/auth.tsx` сохранено закрытие межвкладочного обмена, но очистка кэша выполняется при переходе из другого состояния/аккаунта, а не повторно для уже подтверждённого гостя. Историческая связка с дневником описана в handoff; защитная проверка есть в текущем коде. Нельзя исправлять её отказом от очистки приватного кэша при смене аккаунта.

**Дневник.** Общий виджет выбирает последнюю публичную запись настроенного сообщества. Пользователь обнаружил, что переходы SPA не обновляли запись. `components/DevelopmentWidget.tsx` сейчас явно refetch при изменении `location.key`, дополнительно опрашивает раз в минуту. Shared layout может оставаться смонтированным между маршрутами, поэтому одного запроса на mount недостаточно. Публичная ссылка из дневника должна открываться гостю без обязательного входа.

**Команда.** `SiteTeamSettings` хранит ID аккаунтов, а сервер получает актуальные ники из `User`. Разработчики, художники и тестировщики задаются администратором, модераторы/администраторы выводятся по действующим ролям. Хранить список никнеймов в статическом тексте означало бы рассинхронизацию после переименования. Сохранённые старые тексты очищаются от встроенного дублирующего списка. Автоматическое сопоставление исторических имён с аккаунтами без подтверждения не выполнялось.

**Граница прав.** Тексты сайта, выбор дневника, команда и тестовый доступ доступны администратору, не любому модератору. Роли сотрудников Bubble и роли внутри конкретного сообщества различаются. Файлы — `controllers/siteContentController.ts`, `controllers/developmentWidgetController.ts`, `routes/index.ts`, соответствующие компоненты настроек и модели. Пользователь отдельно запретил добавлять пользовательское соглашение и политику обработки данных в рамках этой работы.

## 8. Онлайн зависит от отдельного realtime-процесса — #85

**Сообщено пользователем.** На локальном сервере виджет выдавал ошибку. **Историческая диагностика по handoff.** Процесс realtime наследовал общий `PORT` API. Добавлен приоритетный `REALTIME_PORT`; сейчас `config.ts` читает `REALTIME_PORT ?? PORT ?? 4100`. Для исправности всей цепочки также нужны корректные `REALTIME_URL`, `REALTIME_SECRET` и клиентский URL Socket.IO.

**Семантика счётчика.** Внутренний защищённый `/internal/online-count` возвращает `online.size`, API передаёт его браузеру. Это число уникальных подключённых аккаунтов текущего процесса, а не число вкладок или всех зарегистрированных пользователей. Ошибка связи должна отличаться от настоящего нуля.

**Ограничение.** Счётчик в памяти одного realtime-процесса сам по себе не обеспечивает общий онлайн при нескольких репликах. Нужна отдельная схема агрегации; её реализация этим чатом не подтверждена.

## 9. Удаление модератором — #89, #88

**Решение.** Удаление чужой записи из карточки переиспользует защищённую модерацию с обязательной причиной и журналом. Пользователь потребовал тот же выбор причин, что при обработке жалобы, плюс собственный вариант. Общие причины находятся в `apps/web/src/lib/moderationReasons.ts`, диалог — в `pages/ModerationPage.tsx` и вызывающих компонентах карточки.

**Вывод.** Кнопка в другом месте интерфейса не должна создавать второй путь удаления с отличающимися правами, очисткой вложений или журналированием. Отдельно проверять собственную запись, чужую запись, публикацию сообщества и сотрудника без нужных полномочий. Закрытие окна по фону не должно отправлять удаление.

## 10. Обновление PWA — #96

**Сообщено пользователем.** Баннер обновления появлялся, но действие не срабатывало. Историческая точная причина первого отказа недоступна; нельзя утверждать, что это была исключительно прозрачная рамка или кеш браузера.

**Решение, подтверждено чтением кода.** `lib/pwa.ts` заново получает registration, проверяет фактический waiting worker, посылает `SKIP_WAITING`; если ожидающего worker нет либо он не отвечает, выполняет резервную перезагрузку. Флаги предотвращают повторное действие и повторную перезагрузку. Вторая вкладка могла активировать worker между показом баннера и нажатием.

**Связь с кешированием.** `public/sw.js` после слияния получил v11, исключает `/api`, `/uploads`, `/socket.io`, перепроверяет навигационный HTML и не кеширует HTML под URL отсутствующего JS-модуля. Смена версии кеша нужна вместе с логикой обновления; она не заменяет корректные ответы Nginx.

**Проверка.** Нужна собранная production-версия: dev-сервер намеренно не регистрирует service worker. Исторические Playwright-сценарии проверяли регистрацию, обновление, Socket.IO и offline shell. Реальное обновление всех ранее установленных экземпляров и физические телефоны не подтверждены.

## 11. Шлюз тестового стенда и инцидент запуска — #95

**Архитектура.** `docker-compose.test-gate.yml` добавляет отдельный сервис `tools/test-gate/server.mjs`; Nginx через `auth_request` защищает SPA, API, uploads и Socket.IO. Это дополнение к обычному Compose. Управление режимом и общей парой логин/пароль — в админке, данные сохраняются в MongoDB. Смена настроек меняет version и отзывает прежние тестовые сеансы. Служебные вызовы шлюза к API защищены отдельным `TEST_GATE_SECRET`.

**Подтверждено текущим чтением.** `controllers/testGateController.ts` хранит bcrypt-хеш предварительного SHA-256 digest пароля, проверяет служебный ключ и не выдаёт хеш в настройках. `lib/api.ts` распознаёт перенаправление на `/__test_gate/login`; проверка включена и в refresh, и в обычные запросы. При объединении с сетевой веткой перед обработкой ответа сохранена проверка поколения сеанса.

**Инцидент после слияния, сообщил пользователь.** Compose завершился на интерполяции `services.api.environment.TEST_GATE_SECRET` и `services.test-gate.environment.TEST_GATE_SECRET`. **Подтверждённая причина конфигурации.** Override требует `${TEST_GATE_SECRET:?Set TEST_GATE_SECRET}` в обоих сервисах. Проверка выполняется до запуска контейнеров. Редактирование режима через админку не заменяет этот секрет окружения.

**Разъяснённое исправление, выполнение не подтверждено.** Передать одинаковое непустое случайное значение обоим сервисам через фактический env-файл запуска, в тестовом workflow — `/opt/bubble/.env.production`. Пользовательский пароль шлюза и служебный секрет — разные сущности. Для обычной локальной разработки можно запускать Compose без gate override. Секреты не коммитить. Отсутствие `git add` само по себе не вызывает ошибку интерполяции; отдельно проверять, завершено ли слияние и присутствуют ли нужные файлы в доставленной ревизии.

**Неочевидная зависимость при объединении веток.** Override монтирует `nginx/test-gate.conf` поверх стандартного `nginx/default.conf`. Новые правила develop для assets, HTML и service worker не попадали в тестовый стенд автоматически. Они перенесены в gate-конфиг: 404/no-store для отсутствующих assets, перепроверка HTML/SW, private immutable для версионированных assets. Контроль входа сохранён. Временный контейнер Nginx без внешней сети исторически подтвердил заголовки, 404 и redirect гостя на вход.

**Граница.** Прямые ссылки внешнего хранилища не становятся защищёнными шлюзом только от включения Nginx auth_request; ограничения таких ссылок требуют отдельной оценки.
