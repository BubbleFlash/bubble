# План диагностики и журнал решений

**Решение этапа 3 — ограничить монтирование карточек в авторизованной ленте.** В обеих парах данные 240 постов оставались доступными, а сокращение активного дерева убрало большую часть задержки. Для первой реализации выбран обратимый оконный вариант на штатном прокручиваемом элементе. Его пригодность для выпуска определяется сравнительным прогоном и регрессиями. [Измерения](BASELINE.md) · [Перепроверка событий Layout](FINDINGS.md).

Реализация и контрольные прогоны этапа 4A документированы отдельно. Работает окно с переменной высотой на штатном scroller и фиксированным запасом около одного viewport, необходимости менять запас по скорости жеста в проведённой проверке не обнаружено. [Отчёт 4A](WINDOW-4A.md).

## Архитектура для этапа 4

**Точка входа.** Подключить окно только в `FeedPage` для «Подписок» и «Всех записей». Адаптер получает текущие данные `PostList`; границы API, ключи Query, мутации и серверная пагинация сохраняют свои контракты. Профиль, сообщества, поиск и отдельная запись продолжают использовать свои текущие маршруты. Изолировать кандидат флагом локальной сборки или режима проверки, чтобы запускать A/B из одной ревизии.

**Выбор механизма.** Первый кандидат — окно последовательных строк в нормальном потоке со spacer до и после окна. Это минимальное продолжение проверенного опыта и оставляет DOM карточек, меню и порталов в существующей геометрии. Пробная реализация начинается с одного viewport запаса сверху и снизу, с гистерезисом при смене окна. Пересчёт диапазона — не чаще одного rAF на scroll, React обновляется при изменении границ. Дискретные сегменты проще считать, но граница сегмента добавляет пачку mount и может дать паузу. React Virtuoso умеет использовать document scroller. TanStack Virtual предоставляет управление scroller, оценкой размера, измерением и диапазоном. Это запасные варианты, если собственное окно потребует сложной логики коррекции или не выдержит быстрый скролл и закрепление активной строки. Скорость библиотек на Bubble пока не измерена. [React Virtuoso](https://virtuoso.dev/react-virtuoso/virtuoso/window-scrolling/) · [TanStack Virtual](https://tanstack.com/virtual/latest/docs/api/virtualizer).

**Геометрия.** Использовать `getPageScroller()` и координаты относительно начала списка. Высоту измерять у смонтированных строк одним ResizeObserver и хранить по `post.id` с привязкой к ширине списка и настройкам шрифта. В высоту входит межкарточный отступ. Для не измеренных строк использовать оценку по виду карточки. Применять измерения пачкой, сохранять `postId` опорной строки и её отступ от видимой границы. Высоту, изменившуюся выше опоры, компенсировать один раз на пачку. Для той же области исключить двойную коррекцию нативным scroll anchoring. Проверить дробные размеры, поздние изображения, смену ширины, быстрый drag scrollbar и восстановление в обе стороны. После большого скачка сначала построить окно вокруг позиции, потом уточнить его по фактическим высотам.

**Пагинация и восстановление.** Sentinel и кнопка догрузки остаются после полного оценочного объёма списка. Дозагрузка изменяет хвост, корректировка наверху допустима только при фактическом изменении порядка или размеров выше опоры. На Back восстанавливать пару `postId + offset` для ключа истории и вкладки ленты в пределах текущего аккаунта. Сначала смонтировать окно с опорой из кеша, затем применить offset. Если пост исчез, взять соседний доступный ID. Обычное нажатие вкладки использует действующий `refreshFeed` и возврат наверх. Никогда не обходить ограничения доступа к записи ради scroll restoration.

**Состояние карточки.** DTO и данные обсуждений остаются в Query, аудио — у текущего провайдера. Для открытого обсуждения хранить по ID просмотра раскрытие, текст, ID адресата и список вложений, чтобы скролл сохранял незавершённый ввод. Для галереи сохранять номер или URL выбранного слайда, для текста — факт раскрытия. При монтировании восстановить это состояние до первого измерения. Очищать состояние ленты при смене аккаунта, при удалении записи и при завершении его жизненного цикла. Обычный текстовый черновик хранится как данные. Черновик с активной загрузкой, открытая модалка, фокус, выделение и IME временно удерживают соответствующую строку, даже если для неё нужен отдельный промежуток spacer. Проверить явное освобождение такого удержания и object URL при завершении или отмене. Не держать по тяжёлому поддереву на каждый ранее открытый комментарий. Клавиатурный переход за пределы окна должен монтировать соседние строки в логическом порядке и сохранять рабочий Tab.

**Что измерять при реализации.** Сначала провести одинаковый прогон окна и исходной ленты при 240 на desktop и 4× touch. Считать p95/p99 интервалов движения и ввода, `Layout`, сдвиг опоры и число принудительных перемонтирований. Увеличить глубину до 500/1000, когда пройдены smoke и проверки якоря, чтобы оценить независимость числа строк и задержек от глубины. Отличимый выигрыш сверять внутри пар, абсолютные значения фиксировать отдельно. Предварительная цель при схожем видимом контенте — 10–15% предельной деградации относительно малой глубины, а на CI — структурная проверка размера окна, корректности курсоров и состояния. Численный предел активных строк зависит от высоты viewport, overscan и явно удержанных строк. Для desktop-функциональности использовать существующие тесты лайков, галереи и комментариев. Диагностический transform исходного PostList для старой контрольной сборки при изменении компонента привязать к сохранённой исходной ревизии или обновить точку подключения.

**Самостоятельные вопросы мобильного профиля и медиа.** CSS упрощение визуальных эффектов дало частичный результат. До продуктовой правки проверить один switch для узкого clip-path с сопоставимым жестом, кадрами с фактическим смещением и визуальной проверкой стыка шапки. Для галереи отдельно измерить готовый слайд фиксированной высоты и штатную смену высоты, затем одинаковый холодный слайд с работающей соседней предзагрузкой и без неё. Проверять Resource Timing, trace и пиксели отдельно. Ограниченный mount остаётся первым изменением для глубокой ленты. Коррекции доставки медиа, CSS или приоритета аватаров вводить по результатам соответствующих опытов. Порядок не требует от владельца выбирать библиотеку или визуальный компромисс до первого измеренного кандидата.

## Открытые вопросы перед реализацией и приёмкой

1. Какие операции инвалидируют широкое дерево layout в Chrome при малом числе dirty objects? В трассах есть обычный lifecycle кадра и синхронный layout на обработке ввода. При необходимости снять короткую локальную сборку с source maps и сопоставить стеки с видимостью, измерениями текста, раскрытием обсуждения и изменением размеров галереи.
2. Как ограничить активное дерево и сохранить переменную высоту и положение? Проверить подвижное окно и сегменты по якорю при движении в обе стороны, раскрытии комментария, подгрузке фото, открытии карточки и возврате. Отдельно выбрать владельца черновика, фокуса и выбранного слайда при размонтировании.
3. Какие из затрат мобильной оболочки и задержки показа медиа требуют самостоятельного решения? Проверить это по отдельным сериям, прежде чем распространять результат desktop mount на мобильный профиль.
4. Какие условия можно превратить в стабильный регрессионный порог? Использовать измеренный разброс и структурные ограничения. Сохранить оптимистическое поведение лайков, клавиатуру, навигацию и особенности физического Android.

Пункты 3–6 выбираются по воспроизведённому симптому. После воспроизводимого парного эффекта и независимого подтверждения на другой контрольной глубине прекращать перебор вариантов по этой причине. Контрольные глубины и проверка остальных симптомов сохраняются. При нескольких вкладах записать остаток после каждого вмешательства. Различия меньше разброса или уменьшение DOM без изменения пользовательской метрики не дают основания для продуктовой правки.

## Почему выбран этот стенд

- Штатный candidate уже строит настоящий production bundle. Сохранить обычные маршруты, оболочку, Query, тач-жесты и реальный цикл изображений. Исходники сценариев и локальный preview можно переиспользовать без новой production-зависимости. [Инфраструктура](../../tools/site-checks/preview.ts).
- Для performance-сценария подавать API и фотографии по HTTP с loopback. В штатных функциональных тестах `page.route("**/*")` включает перехват. Установленный Chromium-драйвер Playwright при таком перехвате отправляет `Network.setCacheDisabled`. Повторный просмотр в этих тестах нельзя считать проверкой браузерного HTTP-кеша. Серверные заголовки, cache flags и число фактических обращений позволят подтвердить прогрев. Локальные фикстуры должны работать без внешних доменов. [Существующие моки](../../tools/site-checks/candidate.spec.ts).
- Во время обычных пользовательских проходов собирать лёгкие счётчики. Короткие окна с профилированием JS, скриншотами и снимками памяти снимать при необходимости. Фиксировать стоимость самой инструментации контрольным прогоном. Lighthouse Navigation/Timespan/Snapshot оставить для вспомогательных вопросов.

## Условие перехода к проектированию

После команды владельца на этап 3 для каждого воспроизведённого симптома связать в отчёте **действие → пользовательская метрика → конкретный участок trace → парное вмешательство → остаточная задержка**. Отдельно перечислить условия, в которых воспроизведение не удалось. Для сравнения вариантов нужны стабильность повторов и измеренный эффект, абсолютные бюджеты уточняются после baseline.

Если подтвердится вклад числа карточек, сравнить минимальное движущееся окно с сегментами, React Virtuoso или TanStack Virtual на репрезентативных карточках. Проверить переменную высоту, стоимость перемонтирования, сохранение якоря/Back, догрузку и повторные запросы, черновики, фокус, выделение, клавиатуру, порталы, аудио и доступность. Для самостоятельного вклада медиа или оболочки выбрать решение по соответствующей трассе. Защиту предыдущих исправлений по лайкам, пропорциям фото, раскладке и теме включить в дальнейшее сравнение. Решение о реализации относится к этапу 4 и требует отдельной команды владельца.
