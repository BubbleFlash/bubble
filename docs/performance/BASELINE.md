## Воспроизведение этапа 2

Из корня репозитория. Запускать серии последовательно, чтобы прогоны не конкурировали за CPU. Последний аргумент задаёт число записей в фикстуре, по умолчанию 240.

```powershell
node tools/site-checks/feed-perf.mjs depth 3 desktop 240
node tools/site-checks/feed-perf.mjs mount 2 desktop 240
node tools/site-checks/feed-perf.mjs effects 3 mobile 20
node tools/site-checks/feed-perf.mjs media 3 mobile 20
$env:BUBBLE_PERF_FILMSTRIP = '1'
node tools/site-checks/feed-perf.mjs media 1 mobile 20
$env:BUBBLE_PERF_FILMSTRIP = $null
$env:BUBBLE_PERF_SCROLL_ONLY = '1'
node tools/site-checks/feed-perf.mjs depth 2 mobile 240
node tools/site-checks/feed-perf.mjs session 1 desktop 240
$env:BUBBLE_PERF_SCROLL_ONLY = $null
node tools/site-checks/feed-perf-report.mjs <каталог-прогона>
```

Стенд собирает приложение в отдельный подкаталог прогона. Фикстуры по HTTP на loopback, по 20 постов через штатный sentinel, с прокруткой через несколько карточек между страницами. В окнах замера ПК получает пакеты wheel, мобильный профиль — последовательные CDP touch events, поле комментария — посимвольный ввод с переносом. Опорные карточки `perf-13` и `perf-233` имеют одинаковый период набора текста и вложений. Прогоны начинают в свежем контексте Chrome. В режиме `mount` одинаковая сборка для обоих вариантов, один вариант заменяет первые 220 карточек проставкой после штатной догрузки и корректирует позицию относительно видимой карточки. Порядок пары меняется на каждом повторе. API, изображения и frontend используют один origin. [Фикстуры](../../tools/site-checks/feed-perf-fixtures.mjs) · [Сценарий](../../tools/site-checks/feed-perf.mjs) · [Обработка трасс](../../tools/site-checks/feed-perf-report.mjs).

В каждом каталоге есть `manifest.json` с конфигурацией и SHA-256 набора, отдельный JSON на вариант и повтор с сетевыми событиями и ответами сервера, `*.trace.json.gz` с исходной записью и `summary.json` после обработки. В окнах `bubble:start:<действие>`/ `bubble:end:<действие>` скрипт вычисляет интервалы между завершениями `PipelineReporter` в состояниях `STATE_PRESENTED_ALL` и `STATE_PRESENTED_PARTIAL` доминирующего layer tree. P95 по клавишам берётся из `EventLatency(KEY_PRESSED)` с display trace ID. События браузера, значения rAF и процентили в каждом повторе можно проверить независимо. Время движка включает вложенные события и параллельные потоки, поэтому столбцы разных категорий нельзя складывать.

Интервалы при жесте относятся к доставке ввода этим драйвером. Его шаги отправляются последовательно с ожиданием ответа CDP или Playwright. Мобильный профиль ограничивает CPU и задаёт touch viewport. В сериях с диагностикой GPU Chrome сообщил ANGLE/D3D11 на NVIDIA GTX 1650 Ti с включённой растеризацией. Результат не описывает GPU, память и тепловой режим Honor 9 Lite. Для начальной загрузки и подготовки позиции в этих мобильных сериях CPU оставался на 1×.

## Протокол для этапа 2

**Единица сравнения** — один и тот же жест или взаимодействие на сопоставимом видимом фрагменте ленты. Для глубины фиксировать количество полученных постов и порядковый номер записи, до которой пользователь дошёл. Отдельно записывать количество смонтированных карточек. Это позволит сравнить A/B даже при изменении overscan или ранней догрузке.

1. **Данные.** Детерминированные 1000 уникальных записей, стабильный seed и хеш набора. Ответы по штатному курсору по 20. На каждой глубине предусмотреть сопоставимый фрагмент с коротким и длинным текстом, фотографиями разной высоты, каруселью с различимыми слайдами, аватарами нескольких авторов, комментариями, ссылками и аудиовложением. Сохранять хеши, размеры, форматы изображений и число уникальных URL. Помечать источник данных, например `synthetic-http` или изолированный реальный API. Одинаковый логотип либо SVG-заглушка скрывают очередь сетевых загрузок и стоимость декодирования.
2. **Условия.** Записать SHA и diff приложения, build ID, версии ОС/браузера/Playwright, CPU/GPU, доступную память, режим питания, headless/headed, программный или аппаратный рендер, частоту обновления, viewport, DPR, touch/UA, SW, CPU multiplier и параметры сети. Один foreground-контекст, один worker. Зафиксировать время/фоновые события, шрифты, тему и положение курсора. Проверить в trace, что выбранный запуск даёт события представления кадров. Если недоступны — обозначить пробел и проверить другой режим Chrome.
3. **Проход.** Начать с desktop 1× и мобильного touch-профиля 4× как отдельных серий. Достигать 20, 100, 240, 500 и 1000 в рамках последовательного чтения через колесо или CDP touch-жесты. Фиксировать паузы между действиями и ID опорной карточки. На каждой достигнутой глубине отмечать отдельными временными окнами простой, обычный жест, ввод и смену фото. Повторно прокручивать тот же участок в обратную сторону. Холодное открытие и повторный проход с накопленным состоянием хранить раздельно от нового открытия на прогретом HTTP-кеше.
4. **Достоверность.** Короткая предварительная пара 20/240 проверяет различимость сигнала и правильность разметки до дорогих прогонов. Рабочая отправная точка — три независимых повтора на условие, с медианой и разбросом результатов между прогонами. Для P95/P99 хранить необработанные выборки, число событий и длительность окна. Для редких взаимодействий накапливать достаточно повторов, при малой выборке прямо отмечать ограничение квантилей. A/B проводить на одном браузере, seed, скорости, настройках, в чередующемся порядке. При разбросе порядка эффекта повторить пару. Новая методика требует переснять обе стороны.
5. **Углубление.** Профиль 6× или откалиброванный слабый Android, ограниченная сеть с заданными RTT и пропускной способностью, 10–20 минут непрерывного использования и сравнение холодного/прогретого кеша входят в программу. Выбирать те комбинации, которые различают конкурирующие объяснения. Для памяти отдельно провести возврат к началу, переход с ленты и несколько одинаковых циклов. Физический Honor вести отдельной серией с моделью, версией ОС и браузера, температурным состоянием и реальным жестом.
