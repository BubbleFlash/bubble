## Редактирование и скрытие из ленты — #120, #122

- Автор может редактировать личную запись в течение пяти минут после публикации. Сервер проверяет срок при сохранении, изменения вложений используют существующий редактор записей.
- Через меню записи можно скрыть из ленты личные публикации пользователя или публикации сообщества. Скрытие пользователя не влияет на его записи в сообществах. Настройки хранятся в аккаунте, отмена доступна на странице соответствующего профиля или сообщества. Репост другого автора остаётся в ленте.

## Закрепление и онлайн — #117, #118

- На личной странице и странице сообщества можно закрепить по одной записи. Закрепление в сообществе доступно управляющим с ролью редактора и выше. Владелец страницы закрепляет свои записи. Закреплённая запись выводится первой с отметкой.
- Списки друзей и поиск людей показывают статус онлайн. Друзья онлайн сортируются выше, данные списка обновляются каждые 30 секунд. Статус получается из realtime пакетами по 50 пользователей. При изменении статуса между страницами порядок может измениться. Отображение статуса на остальных поверхностях приложения ещё требует доработки.
- В списке личных переписок статус собеседника обновляется запросом раз в 30 секунд. В открытом диалоге также используются события присутствия Socket.IO. Отметка закрепления расположена после строки автора, чтобы не нарушать сетку карточки.

## Лимиты HTTP-запросов — #111

- Лимитеры API выключены по умолчанию. В «Панели модерации» → «Лимиты» администратор управляет общим переключателем и каждым правилом отдельно: включает его, задаёт число запросов и длительность окна в секундах. Правила можно сохранить заранее и активировать общим переключателем позже.
- Настройки хранятся в MongoDB и применяются остальными экземплярами API при обновлении кеша (5 секунд). При изменении правила его счётчик начинается с нуля. Раздел управления доступен администратору при исчерпании общего лимита IP.
- Переключатель относится к HTTP-лимитерам приложения. Ограничения Socket.IO, тестового шлюза Nginx и внешнего прокси управляются отдельно.

Socket.IO клиент переключается на polling при отказе WebSocket. Причину HTTP 400 при WebSocket upgrade на тестовом стенде требуется проверить по фактической цепочке Cloudflare и Nginx. В журнал ошибок и CSV добавлены категория, статус внешнего сервиса и Request ID последнего события. При отсутствии старых полей используется `unknown`.

При отказах рукопожатия Engine.IO пишет код, причину, транспорт, наличие заголовков Upgrade и Connection и идентификатор Cloudflare в журнал realtime. Для сопоставления с внешней проверкой используйте `CF-Ray`. Частота этих записей ограничена.

При первоначальной проверке сеанса Socket.IO один раз повторяет запрос к API после сетевой ошибки или ответа `5xx`. Ответы `401` и `403` сразу отклоняют подключение. Если API остаётся недоступен, подключение отклоняется и сервис записывает результат проверки в журнал.

Нагрузочный сценарий для тестового сервера находится в `tools/load-check/staging.mts`. Параметры, состав операций и ограничения описаны в [PERFORMANCE.md](PERFORMANCE.md).

## Мониторинг в админке

- Ошибка загрузки JS-модуля попадает в журнал с категорией `chunk` и шаблоном страницы. Вкладка с доступной сетью и без выбранного трека один раз автоматически перезагружает страницу за десять минут. С выбранным треком Bubble сохраняет плеер и предлагает ручное обновление. Nginx отдаёт 404 для отсутствующих файлов в `/assets/` и требует перепроверять HTML и service worker. Service worker не кэширует Socket.IO.
- Восстановление сеанса имеет отдельный лимит в 300 запросов за 15 минут на IP до запроса к базе. Это прежний потолок запросов с IP, выделенный для восстановления. Для одновременного входа 50 пользователей с действующими сеансами требуется 50 запросов. После проверки cookie действует отдельный лимит в 20 за 15 минут на аккаунт. Клиент делит паузу `Retry-After` между вкладками и повторяет временные сбои с задержкой. Обычные лайки и чтение списка жалоб с подписанным токеном используют лимит аккаунта.
- HTTP-метрики включают выдачу файлов через `/uploads/`. В браузерных сетевых событиях отмечаются отказ авторизации Socket.IO и переход на polling.
- «Админка» → «Мониторинг» содержит вкладки «Ошибки приложения», «Метрики API» и «Сеть и 429». У всех есть выгрузка CSV. Для метрик и сетевых событий доступны периоды 1 час, 24 часа и 7 дней, для сетевых событий есть фильтры по `429`, `5xx` и сбоям соединения.
- API сохраняет агрегаты в MongoDB по пятиминутным интервалам, записи удаляются через 8 дней. Длительность запросов измеряется на API, p95/p99 получаются из гистограммы. Новый лимитер сбора браузерных событий имеет отдельный бюджет. Запросы и политика лимитеров сайта сохранены.
- Серверный `429` показывает имя лимитера, порог, окно и `Retry-After`. Браузер отдельно сообщает об HTTP `429`/`5xx`, сетевых сбоях и проблемах Socket.IO. Идентификаторы `Request ID` и `CF-Ray` помогают сверять образец с журналами. Границы сбора и команда локальной проверки описаны в [PERFORMANCE.md](PERFORMANCE.md).

## Загрузка данных между вкладками

- Обновление сеанса сериализуется с входом и выходом через Web Locks. Устаревший ответ refresh с `401` больше не очищает cookie, которую успела обновить другая вкладка. Вход, выход и смена аккаунта синхронизируются между вкладками по идентификатору состояния сеанса, токены в браузерное хранилище не добавлены.
- Вкладки с подтверждённым аккаунтом обмениваются свежей первой страницей ленты и двумя счётчиками через `BroadcastChannel`. Данные живут в памяти. События Socket.IO обновляют записи и уведомления, активные экраны сверяются с API после переподключения. Для скрытых вкладок инвалидации откладывают REST до активации. Резервный polling остаётся включённым.
- `npm run check:tabs` проверяет открытие от одной до пяти вкладок с реальным API, Socket.IO и отдельной MongoDB. Команда и формат измерений описаны в [PERFORMANCE.md](PERFORMANCE.md).

## Модерация Bubble

- Интеграционные тесты модерации запускаются отдельно с локальным MongoDB: в PowerShell задать `$env:BUBBLE_MODERATION_TEST_MONGO_PORT='<порт>'`, затем выполнить `npm run test -w @commune/api -- src/tests/moderation.integration.test.ts`. Тесты создают отдельную случайно названную базу и удаляют её после проверки; хранилище файлов заменено заглушкой. Без этой переменной тесты пропускаются.
- У старых материалов со статусом `removed` содержимое сохраняется до явного повторного удаления. Если очистка хранилища не удалась, материал остаётся недоступным и удаление можно повторить.
- Для навигации модерации и окна жалоб используются PNG-иконки щита и флага из набора Bubble.
- Кнопки действий находятся справа вверху карточки жалобы. Рядом с заголовком панели есть окно со справкой по разделам модерации.
- Фоны поддерживают скрытие, удаление и восстановление скрытого в жалобах и разделе «Контент». Скрытые материалы исключены из мастерской и избранного, их изображения доступны сотрудникам через защищённый маршрут. Состояния, решения по жалобам и действия сохраняются в журнале.
- Действующие предупреждения показаны в карточке пользователя и снимаются по одному с сохранением события в истории. Очередь жалоб обновляется при переходе в раздел и смене фильтров. Жалоба на фон подписана вместе с его названием.
- В «Контенте» отображаются сохранённые текст, фотографии и музыка скрытой записи. Изображения скрытых записей загружаются через API с проверкой роли. После безвозвратного удаления содержимое очищается; для отсутствующих вложений показывается ошибка.
- В шапке слева от уведомлений модераторы и администраторы видят кнопку жалоб. В выпадающем списке показаны последние открытые жалобы всех типов, счётчик обновляется каждые 30 секунд. Выбор карточки открывает конкретную жалобу, включая уже рассмотренную другим модератором.
- В очереди доступны общий список жалоб и фильтры по записям, комментариям и фонам. Скрытие или удаление материала закрывает связанные открытые жалобы. Ранее скрытые или удалённые материалы также приводят жалобы в соответствие при открытии очереди.
- Раздел «Контент» по умолчанию показывает скрытые и удалённые записи и комментарии вместе. Действия на карточках жалоб представлены иконками, формы подтверждения открываются в отдельных Aero-окнах.
- Вкладки панели используют оформление ленты. Жалобы показывают заявителя с аватаром и карточку материала в стиле репоста, в списке и карточке пользователей аватар расположен слева. Причину действия можно выбрать из списка или ввести вручную.
- «Админка» и «Модерация» ведут в панель `/moderation`. В ней есть жалобы на записи и комментарии, поиск пользователей, санкции, история, журнал и список скрытого и удалённого контента. Технические ошибки и назначение модераторов доступны администратору.
- Модераторы могут предупреждать обычных пользователей, ограничивать публикации и временно блокировать аккаунты. Бессрочные блокировки применяет и снимает администратор. Срок временных мер проверяется на сервере при доступе. Блокировка повышает версию сессии, которую REST и Socket.IO сверяют с MongoDB.
- Скрытие контента обратимо. Удаление очищает содержимое и ссылки на вложения, а служебная запись с историей остаётся. Состояние и событие пишутся одной операцией MongoDB. Решение по жалобе, изменение контента и выдача санкции сохраняются отдельными действиями.
- Материалы со старым статусом `removed`, у которых ещё нет `purgedAt`, сохраняют содержимое до явного повторного удаления через панель. В списке показано пояснение. Незавершённое удаление можно повторить из карточки.
- Старые записи без статуса остаются опубликованными, старые жалобы на записи остаются в очереди, а `banned: true` считается бессрочной блокировкой без исторической причины. Жалобы на фоны остаются в прежнем хранилище.

## Уведомления

- Карточка на странице `/notifications` открывает запись или профиль в новой вкладке браузера и сразу отмечается прочитанной.
- Страница событий подгружает всю доступную историю при прокрутке по 30 записей, в том числе внутри выбранной категории. Курсор использует время и ID события. В колокольчике остаётся список последних событий.
- Карточки на странице и в выпадающем меню используют одинаковый промежуток. В компактных карточках меню время выровнено справа на уровне первой строки. Меню оформлено токенами Aero и использует стиль полосы прокрутки основного контейнера.

- В шапке есть колокольчик со счётчиком и выпадающим списком. В нём и на `/notifications` можно выбрать заявки в друзья, лайки или комментарии. Непрочитанные карточки подсвечены. Переход с `/notifications` или закрытие списка отмечает показанные за этот просмотр уведомления прочитанными. При клике на карточку в выпадающем списке прочитанным становится только выбранное уведомление. Запрос передаёт ID и время события, чтобы сохранить статус более новой версии при повторном лайке или заявке.

Скрытые события сохраняются в MongoDB и исключаются из списка, счётчика, звука и push. Общая громкость и выключатель звука сообщений хранятся на конкретном устройстве; сообщения всегда доступны в переписках.

## Управление группами

- Окно управления сохраняет высоту при переключении вкладок. Длинное содержимое прокручивается внутри окна, вкладки используют оформление ленты.

Владелец назначает администраторов и редакторов, снимает роли и выбирает, кто может публиковать записи и репосты, редактировать и удалять записи, менять название, описание и аватар. Администраторы видят настройки прав, меняют оформление при разрешённом уровне доступа и могут исключать обычных участников.
- По умолчанию публикуют все участники. Участники редактируют и удаляют свои записи, редакторы и администраторы могут изменять чужие. Оформление доступно администраторам и владельцу. API проверяет права независимо от видимости кнопок в интерфейсе. Редактор записи меняет текст, фотографии и музыку.
- Владение передаётся действующему участнику после ввода адреса группы. Бывший владелец становится участником. Поле `Community.creator` определяет текущего владельца, роли управляющих привязаны к ID членства. Передача, назначение ролей, изменение прав и исключение участника используют версию состояния доступа. Для существующих групп применяются значения по умолчанию без миграции.
- Проверены полномочия через API на изолированной MongoDB, включая конкуренцию передачи с выходом участника. Сценарии панели, оформления и редактирования записей проверены в Chrome на 1440, 390 и 320 px с локальным API и MongoDB.

## Репосты публикаций и комментариев

- В редакторе публикации доступна видимость «Только друзья». Доступ получают пользователи с взаимной подпиской. Существующие записи «Только я» остаются доступны автору.
- Владелец сообщества может изменить название, описание и аватар. Записи сообщества показывают его название и аватар, а ссылку на автора — над действиями.
- Страница групп открывается на вкладке «Подписки», рядом доступны «Все группы» и «Мои» с группами владельца. В репосте списки групп и диалогов содержат аватары, поиск диалога встроен в поле выбора.

- Кнопка «Поделиться» открывает модальное Aero-окно с необязательной подписью. Можно опубликовать репост в своём профиле, в сообществе с действующим членством или отправить его в личные сообщения. Ссылка на цитату переводит к комментарию на странице исходной записи.
- `POST /posts/reposts` создаёт отдельную запись с собственными реакциями и обсуждением. MongoDB хранит ссылку на источник и идентификаторы предков. По ним API считает репосты публикаций и сообщений для каждого предка. Лайк репоста отдельно ставит лайк оригиналу; лайки каждой записи затем можно снять независимо.
- Карточки загружаются с учётом доступа текущего пользователя и показывают заглушку при удалении или ограничении доступа. После трёх уровней вложенности показывается ссылка на следующую запись. Для записи в профиле доступен режим «Только я». Старые записи без поля видимости считаются публичными. Файловое хранилище по-прежнему использует адреса загрузок, которые выдаются в данных записи только получателям с доступом к её карточке.
- Публиковать и покупать платные записи больше нельзя. Старые записи с ценой скрыты из ленты, профилей, сообществ, поиска и репостов. Их содержимое и история покупок сохранены в БД.
- Сообщения хранят ссылку на источник. Событие Socket.IO содержит признак репоста, а карточка загружается через API с правами участника. Автор исходной записи получает уведомление. При отправке в личные сообщения уведомление ведёт к оригиналу и не содержит данных переписки.
- Интеграционные проверки запускаются с `BUBBLE_REPOST_TEST_MONGO_PORT` и используют отдельную временную базу на локальной MongoDB.
