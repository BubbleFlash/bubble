# Прогоны производительности и доступности Bubble

Цели, метрики и способ сравнения базы с кандидатом описаны в разделе
[«Производительность и измерения»](../BUBBLE_CONTEXT.md#9-производительность-и-измерения).
Здесь находятся команды, требования к окружению и форматы отчётов.

## Локальная сборка и браузерные метрики

Установи зависимости через `npm ci` и запусти из корня репозитория. Для проверки локального
кандидата очисти `BUBBLE_CHECK_URL`, если он остался от прогона доступности.

```powershell
npm run check:site
```

Команда собирает веб-приложение из текущего рабочего дерева и запускает локальный Vite Preview. Playwright подставляет ответы API, поэтому для этого прогона не нужен MongoDB или аккаунт. Chrome и Edge проверяют ленту из 60 записей на ширине 1280 и 390 px, прокрутку, открытие комментариев и переход в запись. Текущий набор тестов и выбор браузеров описаны в [TESTING.md](TESTING.md).

В `test-results/site-candidate.json` в приложении `feed-timings` сохраняются время появления ленты, открытия комментариев и записи, а также 95-й процентиль и максимальный интервал между вызовами `requestAnimationFrame` при прокрутке. Интерпретация замеров и требования к сравнению описаны в [основном контексте](../BUBBLE_CONTEXT.md#9-производительность-и-измерения).

### Повторное открытие вкладок с реальным API

Запустите отдельный экземпляр MongoDB, как для нагрузочной проверки ниже, и задайте `BUBBLE_LOAD_MONGO_PORT`.

```powershell
$env:BUBBLE_TAB_CHECK_BROWSERS = 'chrome,msedge'
$env:BUBBLE_TAB_CHECK_ASSERT = '1'
npm run check:tabs
```

Сценарий собирает текущую веб-версию и использует временную MongoDB, штатный API и Socket.IO на loopback. `check:tabs` запускает Chromium-каналы. Для Firefox или WebKit используй браузерные сценарии `check:site` и отдельную ручную проверку стыка с реальным API. Он измеряет холодное открытие ленты и одновременное открытие 1, 2 и 5 вкладок после прогрева. Отчёт `test-results/site-tabs.json` содержит запросы, статусы и байты ответов по endpoint, время до появления тестовой записи и WebSocket-рукопожатия. Можно указать другой файл через `BUBBLE_TAB_CHECK_REPORT`. Внешние ресурсы и service worker выключены для воспроизводимости. Замер времени зависит от машины и планировщика вкладок.

Режим `BUBBLE_TAB_CHECK_ASSERT=1` проверяет авторизацию, повторные GET, уведомления и их прочтение между вкладками, доставку и изменение сообщений, восстановление после разрыва Socket.IO, выход и смену аккаунта. `BUBBLE_TAB_CHECK_EXPIRE=1` дополнительно сокращает TTL access-токена до 12 секунд в локальном процессе и проверяет автоматический refresh и переподключение.

### Проверка доступности по конкретному сетевому маршруту

```powershell
$env:BUBBLE_CHECK_URL = 'https://test.bubble-web.net'
$env:BUBBLE_CHECK_NETWORK = 'ISP name, no VPN'
npm run check:site
```

Проверка открывает стенд в новом гостевом контексте, ждёт ответы HTML, проверки сеанса и публичной ленты, затем проверяет отображение страницы. Она возвращает ошибку при `429`, даже если HTML главной открылся. В `test-results/site-reachability.json` в приложении `site-diagnostics` сохраняются статусы, тайминги, сбои загрузки и заголовки `CF-Ray`, `X-Request-Id`, `Retry-After`, `RateLimit` и `X-RateLimit-Limiter`, когда они есть. `X-Request-Id` помогает сопоставить ответ с журналом API.

Для сравнения запустите эту же команду из нужной сети, например через мобильного оператора или через уже настроенный VPN. `BUBBLE_CHECK_NETWORK` подписывает результат. Если есть разрешённый HTTP или SOCKS‑прокси, задайте его адрес через `BUBBLE_CHECK_PROXY`. Скопируйте отчёт после каждого маршрута, следующий сетевой прогон перезаписывает этот файл. Для возврата к локальной проверке удалите `Env:BUBBLE_CHECK_URL`.

`BUBBLE_CHECK_BROWSERS` принимает список через запятую. По умолчанию это `chrome,msedge`, можно выбрать один установленный браузер. Для `chromium`, `firefox` и `webkit` установите соответствующий браузер через `npx playwright install <browser>`. Для `opera-gx` задайте полный путь к исполняемому файлу установленной Opera GX в `BUBBLE_OPERA_GX`.

Доступность локальной сборки проверяется на этой машине. Для проверки изменений через Cloudflare нужен отдельный URL с этой сборкой. Запуск по адресу общего стенда показывает состояние уже развёрнутой там версии и выбранного сетевого маршрута.

Lighthouse можно использовать для дополнительного аудита развёрнутого сайта в Chrome.

## Нагрузочный прогон на одном IP (#64, #79)

Для нагрузочного прогона, который запускает ответственный за стенд человек, на тестовом `test.bubble-web.net` подготовлен отдельный сценарий `node --import tsx tools/load-check/staging.mts`. Число пользователей задаётся через `BUBBLE_STAGING_USERS` (20, 50 или 100), длительность через `BUBBLE_STAGING_SECONDS` (30–1200). Он регистрирует помеченные аккаунты и соблюдает `Retry-After`, сохраняет их сеансы в игнорируемом Git файле `test-results/staging-test-accounts.json`, открывает Socket.IO, читает ленту и профили и создаёт ограниченное число тестовых сообщений, публикаций и медиа. Подготовка аккаунтов с одного IP может занять несколько окон лимитера. JSON и CSV отчёты создаются в `test-results`. Тестовые данные на стенде остаются после прогона, CPU и RAM сервера нужно собирать отдельно. Перед использованием файл с учётными данными следует защитить средствами операционной системы и не прикладывать к отчёту.

Для прогона нужна отдельная локальная MongoDB. Тест запускает реальные HTTP и Socket.IO серверы на случайных loopback-портах, создаёт временную базу с тестовыми аккаунтами, записями и комментариями и удаляет только эту базу при завершении. Лимитеры включены. Сценарий не принимает URL удалённой цели.

```powershell
docker run --rm -d --name bubble-load-mongo -p 127.0.0.1::27017 mongo:7
$env:BUBBLE_LOAD_MONGO_PORT = (docker port bubble-load-mongo 27017/tcp).Trim().Split(':')[-1]
npm run check:load -- --users=20
npm run check:load -- --users=50
npm run check:load -- --users=100
docker stop bubble-load-mongo
```

По умолчанию каждая ступень идёт 20 минут. Для быстрой проверки можно передать `--seconds=45`. Виртуальные пользователи имеют отдельные аккаунты и сеансы, но общий IP. Каждый проходит восстановление сеанса, читает и листает ленту, открывает запись и комментарии, переходит в профиль и выполняет фоновые запросы вместе с реальным Socket.IO соединением. Тест начинается с существующих сеансов. Массовый парольный вход, гостевой трафик, публикации и географическую доступность он не моделирует.

Артефакт `test-results/load-bubble-<users>-<seconds>s.json` содержит статусы, имена лимитеров, p50/p95/p99 по API за весь прогон и по минутам, CPU и RSS общего процесса API и realtime, память и число подключений MongoDB. В полном прогоне пользователи обновляют токен и cookie примерно на 14-й минуте. Тест проверяет, что новый токен даёт доступ к ожидаемому аккаунту, и отличает плановое переподключение Socket.IO от сетового сбоя. Отдельные проверки входа, регистрации и загрузки ожидают `429` с `Retry-After` и именем лимитера. Нештатные ответы, неожиданные переподключения или недостигнутая ступень дают ненулевой код выхода. Повторные локальные замеры запускай последовательно и сохраняй отчёты для сравнения.

## Профиль ленты и медиа (#3, #44, #58)

Запусти web через `npm run dev -w @commune/web -- --host 127.0.0.1`, затем `node tools/measure-feed.mjs test-results/feed-profile.json` (каталог для отчёта должен существовать). `PERF_CHANNELS` по умолчанию равен `chrome,msedge`, `PERF_ORIGIN` меняет адрес локального Vite. С `PERF_VERIFY=1` дополнительно проверяются черновик комментария, изоляция часов плеера, GIF, прозрачность изображения и fallback доставки.

Стенд монтирует 60 карточек под реальными React-провайдерами. Запросы и события Audio подставлены. Сценарий считает необязательные запросы, коммиты React при 20 обновлениях времени, rAF и длинные задачи на участке прокрутки, а также размеры синтетического изображения 1200×900. Реальную сеть, качество картинки и аудиотракт проверяй отдельно. [Исторические замеры](PROJECT_HANDOFF.md#производительность-и-медиа--3-44-58-локально).
